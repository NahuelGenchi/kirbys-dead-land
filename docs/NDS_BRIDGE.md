# Original ROM execution bridge

`src/nds/lib.rs` is a headless C ABI around a pinned melonDS build. The supplied Kirby Super Star Ultra USA ROM executes its original ARM controller, physics, animation, ability loading and collision routines. Host terrain and enemy proxies enter that running machine through emulated RAM. No desktop keyboard, emulator window, DS save file or original ROM writes are used.

## Reproducible private build

Run `python3 tools/oracle_build.py`, then `python3 tools/nds_build.py`. The latter accepts only the pinned vendor revisions and the checked wrapper additions in `tools/nds_vendor.py`. Both also accept and apply the checked call hook in `tools/nds_call_patch.py` (see [original ability change](#original-ability-change-102)) and the checked step patch in `tools/nds_step_patch.py` (see [where a source frame ends](#where-a-source-frame-ends-134)); the first build after either is added recompiles the melonDS files it changes. Libraries, source ROM, captured states, rendered sprites and generated evidence remain under `~/.local/share/kirby-dead-cells`.

- ROM: USA `YKWE`, 134217728 bytes, SHA256 `b2573313a582c8dfaf2d93834a670c1ca8f389e5daa744e2dbe1a4ca903f3027`.
- melon-rs: `51f25edaf3b2df63f91d049eff8c38fb289150eb`.
- melonDS: `82fdbc78483f43b310e920e21acc47787cb43564`.
- Initial private state: `oracle/ready2/000.state`, SHA256 `37166a991f37a4e84f7392fd33ca487672d65efae7f32b38e22b7cc2454a9a76`.
- Built library: `oracle/vendor/melon-rs/target/release/libkssu_bridge.so`.
- Provenance: `oracle/bridge-provenance.json`.

The initial state places base Kirby in Green Greens at source center `(43,153.5)`. Its tile map has100 columns and9 rows of24-pixel blocks. Static source RAM facts were checked with the supplied ROM, source traces and disassembly. The external research repositories identified candidate layouts; they were not treated as authoritative gameplay specifications.

## C ABI

All calls use a single owning thread. Pointer arguments must reference valid caller-owned buffers. UTF-8 file paths are null terminated. Integers are little endian; standard C layout applies. Negative returns indicate failure. Do not execute two live emulators concurrently in one process.

| `kssu_skip_idle_main(handle,u8* palette,length)` | Given a 512-byte standard BG palette, engine A's backgrounds and composition are left out of every scanline whose layer capture would read as "no effect" against it: unit on and not blanked, no colour effect control, that palette. | `kssu_read/write(handle,address,bytes,length)` | Bounded4MiB main-RAM access for research and explicit host integration. |
| `kssu_set_ability(handle,u8 ability)` | Arms one original `SetAbility` call (see below) for copy byte 1–25 on the next player update. | `kssu_ability_change_pending(handle)` | 1 until the armed change has returned (2–5 frames: it loads the ability's graphics), then 0. |

`State` field order: `u32 frame,player; i32 x_raw,y_raw; i16 vx_raw,vy_raw,camera_x,camera_y; u8 ability,kind,flags,facing_raw; u32 graphic,animation,state_words[16]`. Positions are16.16 and velocities8.8. `graphic` low16 selects the pose; upper16 identifies original move-frame data. Despite its name, `facing_raw` (player+`0x15`) does not change with facing; its `0x10` bit hides the actor. The original facing is bit 31 of `state_words[11]` (player+`0x6C`), set while Kirby faces left (`NdsState.FacesLeft`).

The original controller's current action is the u16 at `0x020BAF80` and is the same for base Kirby and every tested copy ability: `0406` standing or crouching, `0507` landing, `060A` skid, `060B` walk, `060C` dash, `070D` jump, `070E` fall, `070F` float, `0916` climb, `142C` ability use (inhale, exhale and spit, and every copy-ability attack, including Wheel's roll and Jet's dash), `0B18` slide; `0815` swim, `0509` wall bump or water exit, `0C19` slide recoil and `0F1D` hurt recoil. Falling is clamped to 896 (3.5 pixels per frame) in every state; a larger written velocity is clamped back. The player's velocity is at player+`0x88` (x) and +`0x8A` (y), in 1/256 pixel; the original moves on a copy of the horizontal velocity at +`0x98`, so clearing a horizontal velocity takes both, while the vertical one is read from +`0x8A`. Its floor test starts from where its previous frame ended: a host move that leaves less than one fall step to a floor carries Kirby a fraction of a pixel into it for a frame. Slopes are sampled at Kirby's centre at whole pixel columns. Hardware OAM read after `kssu_step` describes the previous source frame: pair it with the state captured before the next `kssu_world`, which shifts the player by a whole cell when the window moves, and moves the source camera's scroll position with it (the original camera then follows Kirby from there, at most 16 px a frame). The runtime moves the window with `kssu_world` only by whole cells and moves Kirby alone with `kssu_move_player` for host movement (speed match, stomp descent): moving everything with him dragged his thrown bombs and other objects along. The player's controller block (player+`0x40`) counts the current pose's remaining frames at +`0x6C8` and moves to the next pose on the frame the count is zero; the runtime takes extra frames off it during walks and dashes at the matched speed.

`Hit`: `u32 address,owner,slot; i16 bounds[4]; u32 definition; u16 words[14]`. Bounds are world `[left,top,right,bottom]`, not width/height. `words[2]` is signed damage. Use original proxy HP changes for native debounce, recoil and repeated hits; comparing an attack slot alone does not implement source collision semantics.

`Proxy`: `u32 entity,flags; i32 x_raw,y_raw,hp; u32 update`. Flags:1 present,2 original capture/control state,4 swallowed,8 gone/dead,16 pending initialization,32 original inhaling state,64 native destruction pending,128 original Cook capture. Cook consumes its proxy with flags136 and does not produce a copy evolution. Suplex exposes the visible grabbed clone’s world position and HP while its original node remains hidden. Coordinates are source world render coordinates; the native entity's raw coordinates become relative during inhaling. A completed lifecycle must be acknowledged with `active=false` before rebinding. This runs the original destructor on its normal update turn, freeing original collision/AI allocations before reuse. Pending destruction can take a source frame.

## Original ability change (#102)

The F slot fires a stored limited-use ability without the inhale or swallow, through the routine every original copy change uses: `SetAbility(actor, record, ability)` at `0x0211B734`. The swallow (`0x021140F8`), each limited ability's last-use revert (Crash's is `0x0210D14C`) and the original give-ability routine `0x020AF020` all call it. The player actor is the pointer at `0x02049DF0` (`0x02049EC4` in the seed); its update callback (actor+`0x30`) is `0x020B2714` and its record (actor+`0x40`) is `0x020BAF68`, the first of the per-player records (stride `0x81C`). Record +`0x10..0x15` are six signed-byte fields read and written through `0x020A8214`/`0x020A8278`; field 3 (`0x020BAF7B`) is the copy byte and its only writer. `SetAbility` runs the old ability's exit callback (table `0x0214A038`, 16 bytes per ability), loads the new ability's descriptor, animation (`0x020A2A50`) and graphics (`0x020A6678`), runs its enter callback and refreshes the bottom screen. Writing the copy byte alone does not change the attack; this routine does.

The bridge cannot execute ROM code by itself. `tools/nds_call_patch.py` adds a checked hook to the pinned ARM9 interpreter: when the bridge has armed a call, the next time ARM code is about to run the player update entry `0x020B2714` the interpreter saves r0–r14, runs `SetAbility(actor, record, ability)` with that entry as its return address, then restores the registers and runs the update normally. The routine reads the ability's graphics from the cartridge and so blocks the game thread for 2–5 frames before it returns; the hook state stays pending until then. While idle the interpreter only tests one global per instruction. `kssu_set_ability` applies the original give-ability routine's own test first (player field 2 == 1 and action group, record +`0x19`, of 4, 6, 7 or 8) and refuses while Kirby inhales: called during an attack (group `0x14`) or with a mouthful the routine left Kirby in the attack action for good. Savestates written by `kssu_save_state` end with a `KSSUHK01` trailer holding the hook state and its saved registers, so a save taken while a change loads resumes it; any other load clears the hook.

Headless evidence (`tools/nds_tests.py`, cases `f_slot` and `f_slot_save`): from a swallowed Sword, a change during a Sword swing is refused (−2); a change to Crash returns within its first frame, the attack button fires it and the original reverts to base form on frame 267 as from a swallowed Crash; Sword comes back in 4 frames and hits; Mike limited to one shout reverts after it. A save taken while a Mike change was pending, then loaded, finished the change and the shout. (Before #134 a frame ended 71 scanlines after VBlank and saw the same machine a frame apart: Crash after 2 frames, its revert on frame 266, 268 after arming either way, and Sword in 5.) A private research build (write watch, execution log and the same call) matched the normal path for Crash, Paint, Mike and Cook frame for frame (revert on 266, 404, 135 and 445) with the same audio level.

## Where a source frame ends (#134)

The original waits for VBlank (scanline 192) and then runs one logic pass: it reads the buttons, updates every actor and the camera, builds its sprite records (the OBJ manager at `0x020598E0`, sixteen priority lists at `+0x18`) and from them the shadow OAM that the next VBlank copies to the hardware. `NDS::RunFrame` ends at the end of scanline 262, 71 scanlines after that pass began. Kirby alone finishes within them. With a helper the pass is often longer, and the frame ended inside it: Kirby and the camera already updated, the sprite lists emptied and not yet filled again. `kssu_world` then moved every position by a terrain cell under the unfinished pass, and the pass drew Kirby a cell (24 px) away for one frame. Off-screen OBJ pairing failed on the same frames.

`tools/nds_step_patch.py` is a checked addition to the pinned melonDS frame loop. With `kssu_vblank_step` set, `RunFrame` returns as scanline 192 begins, before the VBlank interrupt is taken, and the next call continues that frame. The machine runs the same instructions at the same emulated times; only where a call returns moves, so the bridge meets the original between two passes. A call recognises that point from the machine itself (VCount 192 in an unfinished frame): save states keep their format, and one saved there continues from there. A state saved at the end of a frame (the oracle's seed, any state from before this change) has 192 scanlines left before its VBlank, in which the original only waits. `kssu_open` and `kssu_load_state` run those once (switch value 2) and drop their sound, so every step is one whole frame and delivers one frame of audio. `KSSU_STEP_AT_FRAME_END=1` in the environment keeps the old boundary, for comparison only.

What changes for a reader of the machine:

- Hardware OAM after a step is still one pass behind the state (`NdsRuntime.DisplayedOrigin` is unchanged). The per-scanline layer captures are now of the 192 lines drawn at the end of the step, the picture of that same OAM. The emulator presents those lines as its framebuffer when their frame ends, inside the next step, and a state does not hold them: the first framebuffer after loading a state saved at VBlank is not of that run (`tests/render` steps once first; `tests/background` compares each capture with the next framebuffer).
- Whatever ends between 71 and 263 scanlines after its VBlank is seen one step earlier than before (the ability-change counts above).
- A pass can still take longer than a whole frame: the original reads an ability's or a helper's graphics from the cartridge (three frames for a swallowed Sword and two for its helper in the test scene). `kssu_unfinished_passes` counts the steps that ended with all sixteen sprite lists empty beside a shadow OAM that still has entries. `NdsRuntime.PassUnfinished` tells the last step; on those frames `KirbyNdsProvider.HoldWindow` keeps the terrain window where it is and Kirby's own host movement waits, and the `Kirby pacing` log line reports the count each minute. An elevator carry or a host teleport on such a frame still moves him.

`kssu_world` also moves the original's drawing copy of the camera (`0x0204222E` x, `0x0204222A` y, the camera `kssu_state` reports) with the window. A pass that leaves the scene as it is, as the original does while Kirby takes an ability, does not set that copy again; left behind, the screen position reported for Kirby was a cell from where he was drawn for one frame.

Evidence, all on a private build (`repros/flicker-134`, bridge source SHA-256 `5e4cab4188433cc61fda6022e7cc4bc2d034a9b2691d1a35637f8d06968e2b5c`); the shared bridge binary was not rebuilt:

- Headless replay of the runtime's placement (window rebased every frame, flaps, floats, dashes and attacks both ways, 2,082 frames a scenario, with and without the speed match). Frame-end boundary: with a Sword helper 16 and 39 frames ended inside a pass and Kirby's body OBJ left its place for one frame 5 times and once (12 px or more); without a helper one frame and no jump. VBlank boundary: no frame inside a pass and no jump of even 3 px in the four scenarios.
- `tools/nds_tests.py` case `step_between_passes`: the same replay from the seed state, through a helper's creation and a second Sword load with the window moved a cell under the load, then 622 frames with the helper: no frame ended inside a pass apart from the 8 of the loads, 3 frames held, no one-frame jump, and a state saved at VBlank continues the same. It fails with `KSSU_STEP_AT_FRAME_END=1`. All 84 cases pass.
- `tools/verify_renderer.py` (29 cases, no mismatch), `tools/verify_background.py` (Crash, Paint, Mike and Cook, no mismatch, the same active frames as before), `tools/verify_native_init.py` and `tests/speed` (47 checks) pass.
- Live, isolated profile, Sword given to a helper, then about 65 s of runs and flaps both ways with a 30 fps capture: run `20261013-135009` logged 5 original frames ended inside a pass in its first minute (the Sword and helper loads) and Kirby is never a cell off his path in 1,831 captures. The same build and plan with `KSSU_STEP_AT_FRAME_END=1` (run `20261013-192904`) logged 118 and shows him a cell off in 10 captures.

Not run: the owner's play launcher, a controller, scenes with many host enemies, an elevator during a load. Paint's, Cook's and Mike's revert frames were not measured again at the new boundary.

### Plasma's charge aura after a change (#135)

Owner recording `Screencast From 2026-10-13 12-45-59.mp4`: with Plasma as the main copy, after Crash fired from the F slot every direction tap (Plasma's charge) drew Kirby as a white and orange ball and a row of scrambled Kirby tiles for one frame. The original's own screen shows the same from the machine in the owner's Kirby save and from the seed (Plasma, `kssu_set_ability(23)`, `kssu_set_ability(12)`, direction taps), so it is in the source machine, not in the host renderer.

Plasma's charge aura is an effect of class 9, type 20, sub-type 1 (actor +`0x44`/+`0x45`; init `0x020C8440`, update `0x020C838C`). Plasma's enter callback `0x020FCE98` creates one. The charge-level routine `0x020ABFD4` returns −1 unless the copy byte is 12, and in every case ends in `0x020FB914`, which creates the aura when Kirby has none. `SetAbility` runs Plasma's exit callback `0x020FCED4`, which removes it (`0x020CC3B8(actor, 20, −1, 0)`), but Plasma's pose handler `0x020FBCCC` (table entry `0x02131560`) stays installed until Kirby's pose changes and asks for the level again, so the aura comes back while another copy's graphics are loaded. Skipping that one call (`0x020FBCDC`) left no aura; skipping each of the other three callers of the level routine did not. When Plasma is given back its enter callback creates a second aura. The first is bound to the wrong sprite data: on a charge its sprite record (list 4, attribute `0x000E` instead of `0x0014`) points 12 bytes at a time into memory just below the real piece data, which gives OBJ pieces of the prohibited shape 3 and 64×64 pieces in Kirby's palette after Crash, and ARM9 data aborts in the OAM builder (`0x020101B0`) or at `0x0200F610` after Paint, Mike and Cook. Any `SetAbility` away from Plasma leaves the aura (also to Sword or base form); only the limited copies made it visible. A real swallow of Plasma removes it, and the original's own discard removes aura and sparks in one frame. The other 18 regular copies showed no stray object after the same switch.

Before each source frame `kssu_step` counts the player's auras (`stray_plasma_aura`). Any aura while Kirby is not Plasma, or more than one while he is, arms the call hook with the exit callback's own removal limited to the aura, `0x020CC3B8(actor, 20, 1, 0)`, at the next player update; with more than one under Plasma all are removed and the level routine creates one again in the same frame. No armed or running change is replaced. While the Plasma pose lasts in another copy the aura is removed and created again once per frame (standing as Crash it was still counted each frame, and was gone the frame after the pose handler's call was skipped); it draws nothing there, and an F press leaves that pose with its attack. This also repairs a machine saved with the extra aura.

Headless evidence, with the bridge built in an isolated crate (the shared binary was not replaced): case `f_slot_plasma` (`tools/nds_tests.py`) switches Plasma to Crash and to Paint, fires each, waits for the original's revert, gives Plasma back and taps a direction for 120 frames: no aura in base form, one aura afterwards and no shape-3 OBJ piece. It fails on the bridge without this change (an aura is left after Crash's revert). In a separate sweep of Plasma against Crash, Paint, Mike and Cook, switched with and without firing, the unchanged bridge gave 65 frames with shape-3 pieces for Crash and one data abort for each other case; the changed bridge gave none of either. The machine from the owner's save loaded with two auras, had one after the first step and drew 150 frames with direction taps and no shape-3 piece (55 such frames on the unchanged bridge). All 84 cases passed against the changed bridge, run one at a time. Not run: a live game check.

## Terrain and input

Source block IDs0 and3 mean empty and solid. The bridge reserves130 water,131 one-way,132/133 the two original45-degree slopes, and134 ladders, using original essence bytes80,2F,40,41,0E. Rebase the source local window around the host player each frame; preserve the fractional position within its24-pixel host cell. The original base Kirby center is14.5 pixels above its foot on a flat floor. Source terrain probe caches are rebased along with entity coordinates; velocities and action timers are untouched.

The normal local origin places the source player around X384 and Y96, leaving a100×9 source tile neighborhood. Arbitrary activation teleports may trigger the original short landing animation; allow initial settling before visual comparison. Source flight/jump physics run through the injected terrain, including jumping through one-way platforms and swimming.

Input mask: A1 jump; B2 attack/inhale; Select4 drop ability; Start8 pause; Right16; Left32; Up64; Down128; R256/L512 guard; X1024 helper; Y2048 jump. **Select drops the copy ability; Y does not.**

Ability IDs:1 base;2 Cutter;3 Mirror;4 Beam;5 Fighter;6 Suplex;7 Yo-Yo;8 Wheel;9 Bomb;10 Ice;11 Fire;12 Plasma;13 Ninja;14 Stone;15 Wing;16 Jet;17 Copy;18 Sword;19 Hammer;20 Parasol;21 Paint;22 Mike;23 Crash;24 Cook;25 Sleep. Writing the ability byte alone does not load its graphics/controller and can crash the original game. Always use a real swallow or validated content insertion followed by original DOWN.
